## [0.1.0-beta.47] - 2026-11-14

**The forty-seventh pre-release: with Advanced metrics on, FrameLedger reads NVIDIA's own report of where a frame's
time goes.** On an NVIDIA card, in a Direct3D 12 game that uses NVIDIA Reflex, a session recorded with *Advanced
metrics* on now also stores how long the graphics driver says each stage of a frame took — simulation, render
submit, present, driver, the operating system's queue, the graphics card — as seven lines under *Latency* on the
Advanced page, with a table of the driver's low-latency state. **They are the driver's numbers, not a measurement
by FrameLedger**, and they are not the delay from a click to the screen. The same unsigned installer: verify its
hash against `SHA256SUMS.txt`, then *More info → Run anyway*.

**This is the first release in which the part inside a game makes a call of its own.** Until now it only read what
a game itself passed to the graphics calls FrameLedger intercepts. To read this report it asks the graphics driver,
about once a second, on the game's own thread that presents its frames — two functions of the driver that only
read. It reaches them through NVIDIA's library only where the game had already loaded it, and never loads that
library itself; a copy sitting in the game's own folder is not the driver's and is not used. It is built to step
back rather than disturb a game: a request that takes two thousandths of a second or more, or that goes wrong, is
the last one until the game is closed, and the session says so. **With Advanced metrics off — the default — none
of this happens.** The Disclaimer and the Privacy Policy say all of it; the terms window shows once.

**What it is not, yet.** **No real game has been read.** The reading was written and tested against FrameLedger's
own test program with a stand-in for NVIDIA's library, and measured with a test tool against one driver on one
card (GeForce RTX 5080, driver 32.0.16.2114): there a request takes about three millionths of a second, and none
took a thousandth while the tool, like a game using Reflex, slept between frames. What a game's own threads, frame
generation, another driver or another card do with it is for the first real sessions to say; a game that enforces
Windows' Control Flow Guard on a driver that tool was not run against is not covered. On a busy PC the
two-thousandths limit will now and then switch the reading off for a pause that was Windows' and not the driver's;
the session then says *stopped* with the time, and the next start of the game reads again. The session summary's
latency fields still read N/A, and nothing here is read on Direct3D 11, Vulkan or OpenGL. No test runs the whole
path from the game to the ledger through the real capture agent; the Japanese texts are new and unreviewed.

**Also in this release.** The log of the part inside a game now says how a group of hooks went in or came out —
in one go, or one hook at a time — after two groups in the first real sessions on 0.1.0-beta.46 took far longer than
the rest and the log could not say why. And 0.1.0-beta.46's other half has now been seen in a real game: stopping
the part inside a running game took all twenty-nine hooks out under one stop of 83–86 thousandths of a second,
twice, and the game went on.

**Measured overhead this release.** A presented frame: one more read of one word; too small to measure on the
test program. The request to the driver, once a second while Advanced metrics is on: 2.5–2.6 millionths of a second
at the median after a frame that slept, 8–67 at worst, in three runs alone; 3.4 and 130 on a busy PC. Not measured
in a game.

**Updating from `0.1.0-beta.46`:** Help ▸ Check for updates, then *Restart to update* with no game running. **The
terms are shown once** — Privacy Policy 2.20 and Disclaimer 2.16. No change to the ledger (schema 23) or to the
shared memory's layout (5); the detection rules stay at `2026.11.2`. **The code loaded into a game changed in this
release**, so a game that was running during the update keeps the old part until it is started again.

### Changed

- **The log of the part inside a game says how a group of hooks went in or came out** (owner decision D137). Since
  0.1.0-beta.46 hooks are put into a game in groups, the game's threads stopped once for a group. In the owner's
  first sessions two groups took much longer than the others (0.6 s and 1.3 s against 0.1-0.3 s), and the log
  could not tell one long stop from a group that had to be finished one hook at a time. The `PATCH_BATCH` line now
  reads `install` or `restore` for a group that went in one go, and `install singly` or `restore singly`, with a
  count, for one that did not. Nothing else about hooking changed, and what a game is measured by is the same.

### Fixed

- **For developers: a native test that is cut short no longer counts as passed.** The quality gate's native tests
  were judged by their exit code alone, and a test program that was stopped early with a clean exit code read as
  *Passed* - seen once, when security software removed the test program while the gate ran. Every native test now
  has to print the line it ends on, a test added without one stops the build's configure step, and four tests
  exist only to prove the rule goes red when it should. Nothing a user installs changed.

### Added

- **The part inside a game can read NVIDIA's own latency report, with Advanced metrics on** (owner decisions D132, D136,
  D138-D141). While a session records Advanced metrics, and only then, it asks the graphics driver about once a
  second for its report of a frame's stages - simulation, render submit, present, driver, the operating system's
  queue, the graphics card - and for its low-latency state. It is a call FrameLedger makes itself, on the thread
  that presents the game's frames, through NVIDIA's `nvapi64.dll` only where the game had already loaded it;
  Direct3D 12 only. A copy of that library sitting in the game's own folder is refused. A call that faults or takes
  two milliseconds is the last one until the game is closed. **The Advanced page shows it** under *Latency*: seven
  lines, one a stage, and a table of the driver's low-latency state; the line under a session says what became of
  the read - read, the driver reported no frame, not read and why, or stopped and why. They are the driver's
  numbers, not a measurement by FrameLedger, and no real game had been read when this was written. **Privacy
  Policy 2.20 and Disclaimer 2.16** say what is stored and what the part inside a game now does; the terms window
  will show once.

- **For developers: room in the shared memory for NVIDIA Reflex latency** (owner decisions D136, D138). Ten reserved
  words of the block that carries Advanced metrics from a game are now named for the driver's latency report -
  where the read stands, and a sum for each stage of a frame. Nothing writes them yet and nothing reads them; the
  shared memory's layout version did not change.

- **For developers, nothing a user installs: a probe for NVIDIA Reflex latency** (owner decision D132). An
  unshipped tool, `fl-probe-reflex`, and a stand-in `nvapi64.dll` among the test fixtures measure what it would take
  to read the driver's latency report from inside a game - on FrameLedger's own test program and against the
  installed driver, never in a game. What it found is `docs/spike-notes/31-reflex-route-d-harness.md`. A further
  leg (owner decision D139) measured the same reads while the probe itself used Reflex's sleep, as a game does:
  the reads do not wait behind it. The owner has said to go on to a real game (D136); that work is not in any
  release yet. Nothing in the App, the Agent or the part that runs inside a game changed.
