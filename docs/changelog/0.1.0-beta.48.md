## [0.1.0-beta.48] - 2026-11-14

**The forty-eighth pre-release: NVIDIA's latency report has now been read in real games, and what they showed is
in it.** On the day 0.1.0-beta.47 came out the owner recorded eight sessions with *Advanced metrics* on. The
report was read in Phantom Blade Zero and in Cyberpunk 2077, with frame generation on and off: the driver answered
every second, the slowest request took 65 millionths of a second, nothing was switched off, and no game was
disturbed that the logs can show. Two games that are not Direct3D 12 and one that never loaded NVIDIA's library
were left alone, each with its one line saying why. The same unsigned installer: verify its hash against
`SHA256SUMS.txt`, then *More info → Run anyway*.

**What the first game showed, and what this release does about it.** In Phantom Blade Zero the line called *GPU
render* was longer than the whole frame — 16 thousandths of a second where the total was 5. That line runs from
the moment the graphics card starts on a frame to the moment it ends, **and includes the time the card waited in
between**. NVIDIA's driver also works out the figure without the waiting, and the time from one frame's end to the
next. Both are in the report FrameLedger already asks for, and a session now stores them as **a second chart under
*Latency*, with two lines**: *GPU active render* and *GPU frame time*. Nothing more is asked of the driver. The
old line stays, under a name that says what it includes. **The stages of a frame overlap; they were never parts
that add up to the total**, and the texts now say so.

**Three more things the sessions showed.**
- The table of the driver's low-latency state kept only the *last* frame-generation multiplier: a session that
  generated frames at ×2 and ended in a menu showed 1. It now lists every value the session saw — *1, 2*.
- **Sensors were read every 1.3 seconds where the setting says every second** — on the owner's PC, in nearly every
  session since the series began. The capture agent waited the whole interval *after* each reading, and a reading
  there takes about a third of a second. It now keeps the period. No chart was wrong, because every sample is
  stored with its own time; but a session now has about a third more samples, and readings of the latency report
  no longer fall between two of them. What makes a reading take that long there is not established.
- A session could begin with the last reading of the session before it, in a game that kept running between the
  two. It no longer does.

**What it is not.** Two games on one driver and one card (GeForce RTX 5080, driver 32.0.16.2114) are not every
game. The two new figures have not been seen from a real game yet: a driver may give neither, and the chart is
then simply not there. Reflex switched off in a game's menu, and a game started with Advanced metrics off, have
still not been tried on a real game. They remain the driver's numbers, not a measurement by FrameLedger, and not
the delay from a click to the screen; the session summary's latency fields still read N/A. Nothing here is read
on Direct3D 11, Vulkan or OpenGL. The Japanese texts are new and unreviewed.

**Measured overhead this release.** A presented frame: unchanged. The request to the driver, once a second while
Advanced metrics is on: summing the two further figures adds about 36 billionths of a second to work that follows
the request itself. In the real games of 2026-11-14 the slowest request took 20 to 65 millionths of a second.

**Updating from `0.1.0-beta.47`:** Help ▸ Check for updates, then *Restart to update* with no game running. **The
terms are shown once** — Privacy Policy 2.21 and Disclaimer 2.17. No change to the ledger (schema 23) or to the
shared memory's layout (5); the detection rules stay at `2026.11.2`. **The code loaded into a game changed in this
release**, so a game that was running during the update keeps the old part until it is started again.

### Added

- **Two more lines from NVIDIA's latency report: how long the graphics card was really at work** (owner decision
  D142). In a real game the driver's *GPU render* stage turned out longer than the whole frame: it runs from the
  card's start to its end and includes the time the card waited. With Advanced metrics on, a session now also
  stores two figures the driver works out itself — **GPU active render**, the same stage without the waiting, and
  **GPU frame time**, from the end of one frame's work to the end of the next — as a second chart under *Latency*.
  They come from the report FrameLedger already asks the driver for; nothing more is asked. A driver may give
  neither, and the chart is then not there. Sessions recorded before this release do not have them.

- **For developers: the part inside a game reads two more figures of NVIDIA's latency report, and keeps every
  frame-generation multiplier a session saw** (owner decisions D142, D144). In a real game the driver's span between its two GPU marks was longer than the frame's whole
  — it includes the card's waiting. The driver's own *active* render time and its GPU frame time are members of
  the report FrameLedger already fetches; they are read from it, with **no further call into the driver**. Four
  reserved words of the shared memory carry them and the multipliers seen (layout 5 as it was). `fl_reflex_summary`
  and the injected `[latency]` cases hold it. Measured: +36 ns a read, once a second.

### Changed

- **The *GPU render* line says what it includes** (owner decision D143): *GPU render, start to end (idle time
  included)*, in the three languages. The numbers are the same.
- **The driver's frame-generation multiplier is every value the session saw** (owner decision D144). The table of
  the driver's low-latency state kept only the last one: a session that generated frames at ×2 and ended in a menu
  showed 1. It now shows *1, 2*. Sessions already recorded keep what they stored.
- **The texts say what was read** (owner decision D145). The accuracy statement, the README and the guide said no
  real game had been read; two have been, on one driver. They also say now that the stages overlap and do not add
  up to the total. **Privacy Policy 2.21** names the two new averages; **Disclaimer 2.17** changes only with the
  accuracy statement it carries. The terms window shows once.

### Fixed

- **Sensors were read less often than the setting says** (owner decision D146). With the sensor interval at
  1000 ms, nearly every session on the owner's PC got a sample every 1.3 seconds: the Agent waited the whole
  interval *after* each reading, and a reading there takes about a third of a second (what in it does is not
  established; on a PC where the Agent is not run as administrator it takes a millisecond, and the samples were
  already a second apart). It now keeps the period. No chart was wrong — every sample is stored with its own time — but a session
  has about a third more samples now, and about a quarter of the readings of NVIDIA's latency report no longer
  fall between two samples. For developers: `sensor_blobs.hz` was the constant 1 and is now the rate the
  session's samples had.
- **A session could start with the last read of the session before it.** In a game that kept running between two
  sessions, a read of the driver's latency report that ended after the first session's last tick was taken as the
  second session's first point. A new session now drops it.
