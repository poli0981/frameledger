## [0.1.0-beta.49] - 2026-11-14

**The forty-ninth pre-release: what the owner's sessions on 0.1.0-beta.48 showed, the same day.** Eighteen
sessions, sixteen of them with *Advanced metrics* on — Phantom Blade Zero, Cyberpunk 2077 and Clair Obscur:
Expedition 33, with frame generation on and off, with Reflex on and off. Sensors are now read every second; NVIDIA's driver gave both
of its own GPU times in every report of every game; the table lists every frame-generation multiplier; a game
started with the option off was left alone; the driver was read just the same with Reflex off; and the owner's
word on how the games felt: no hitch. The same unsigned installer: verify its hash against `SHA256SUMS.txt`, then
*More info → Run anyway*. **No legal text changed, so the terms window does not appear.**

**Two things those sessions showed, and what this release does about each.**
- **The *Latency* charts had holes.** After a session's first reading, between 0.4 and 16 % of its samples had
  none. There were two reasons, one on each side. The part inside the game did its once-a-second round a second
  *after* the last one finished — so it fell behind — and whenever the game loaded a library it was woken early,
  published what it had, and asked the driver for nothing new. And the capture agent kept one reading until a
  sample could carry it, and replaced it if another arrived first. Both are mended: the round inside the game is
  now due at fixed moments, and the agent keeps the reading that waits.
- **In Cyberpunk 2077 without frame generation, NVIDIA's *GPU active render* time is longer than the time from the
  card's start on a frame to its end** — which should contain it. Nothing stored can say whether that is the
  driver's arithmetic or the way FrameLedger averages the two (one over every frame, one only over the frames that
  gave a time). **This release changes no number you see.** It counts, frame by frame, how the two stand to each
  other, and writes the counts to the game component's own log, together with the driver's low-latency state and
  its frame-generation multiplier — the owner asked that Reflex and frame generation always be read together. The
  next sessions say which it is; what to do about it is decided then.

**What it is not.** Not a promise that every sample now carries a reading: with both sides on one second a slip
can still leave one without, and the log says how often. The reason given for the agent's half was read from the
code and fits the pattern in the ledger; it has not been measured in a session. Nothing here is read on
Direct3D 11, Vulkan or OpenGL, and the figures remain the driver's, not a measurement by FrameLedger. The log of
the component inside a game grows by about seven lines a minute while *Advanced metrics* reads the driver — a few
tens of kilobytes an hour — and a bug report carries those logs, as it always carried them. A game that closes by
itself loses the last batch of counts, under a minute.

**Measured overhead this release.** A presented frame: unchanged — no line that runs with a present was touched.
The reading of the driver's report, once a second while a session with *Advanced metrics* runs in a Direct3D 12
game: 65 billionths of a second more (424–435 → 490–499 billionths, the same instrument as before), after the
request's own time has been taken. The background thread inside the game: ten readings in 9 996 ms, twenty in
20 002, sixty in 59 997 on the test harness — and the same with another thread waking it eighteen thousand times
in ten seconds, where the code before it published 35 720 times in eight seconds and read nine times.

### Added

- **The frames NVIDIA's latency report gives are counted, for the Overlay's own log** (owner decisions D148,
  D151; nothing new is stored, shown, asked of the driver or read from its report). The owner's sessions on
  0.1.0-beta.48 showed both of the driver's own GPU times in two games — and in Cyberpunk 2077 without frame
  generation an *active render* time longer than the span from the card's start on a frame to its end, which the
  two averages cannot explain: one is over every frame, one only over the frames that gave a time. While a session
  with *Advanced metrics* reads the driver, the Overlay now places each frame by its own two numbers and writes
  the counts to `overlay-<pid>-….log` as `LATENCY_FRAMES` lines, in batches that each belong to **one state of
  the driver's low-latency status and its frame-generation multiplier** — the counts are read together with
  Reflex and frame generation, never apart. About six lines a minute; a game that exits by itself loses the last
  batch, under a minute. A bug report carries those logs, as it carried them before. Measured: 65 billionths of a
  second more for each reading of the report, once a second; a presented frame costs what it did.

### Changed

- **The guide says whose switches the latency table shows**: the driver's, not the game's menu. `bLowLatencyMode`
  is also on when *Low Latency Mode* is set for the game in the NVIDIA App, and `bUseGameSleep` says whether the
  game itself paces its frames through Reflex — in some games only with frame generation on (the owner's word,
  2026-11-14, and what Clair Obscur's sessions of that afternoon read).

### Fixed

- **NVIDIA's latency report is read on a grid of one second, and a busy loader no longer leaves holes in it**
  (owner decision D150; the Overlay's half). After a session's first report, 0.4 to 16 % of its samples carried
  none — the *Latency* charts had gaps. The Overlay's background thread waited a second *after* each round of its
  work, so it fell behind the capture agent, which samples exactly every second; and whenever the game loaded a
  library that thread was woken early, published what it had and asked for no new reading, so the round after it
  had nothing to publish. Its once-a-second round is now due at fixed moments whatever the work took, and a round
  woken early no longer publishes or takes a reading. Two readings are never less than half a second apart.
  Nothing on a game's own threads changed.
- **A reading that waits for a sample is no longer overwritten by the next one** (D150; the capture agent's
  half). The agent kept one reading from the game until a sensor sample could carry it, and replaced it when
  another arrived first. When a reading landed just after a sample, that sample went without and a reading was
  lost a little later — in one session of the owner's, one sample in five for four minutes. Two readings may now
  wait and the older is stored first; a point can stand up to a second after its reading was taken. With the
  sensor interval above one second, not every reading is stored, as before.
