## [0.1.0-beta.23] - 2026-10-14

**The twenty-third pre-release: a game's artwork on its page, in a band that takes the picture's colour, and pages
that open and change session without freezing.** The same unsigned installer: verify its hash against
`SHA256SUMS.txt`, then *More info → Run anyway*.

**Updating from `0.1.0-beta.22`:** Help ▸ Check for updates, then *Restart to update* with no game running. The
Privacy Policy (2.11) is shown once for you to accept. No game is read again: the detection rules (`2026.10.4`) are
beta.22's. The artwork shows by itself for the games Steam or GOG GALAXY installed; **Settings ▸ Games** turns it, or
its colour, off.

### Added

- **A game's page shows its artwork** (owner request 2026-10-14, decisions D60/D61). At the top of the page: the
  banner and the cover the Steam or GOG GALAXY app already keeps on your PC for the game it installed — read where that
  app keeps them, never downloaded and never copied — or an image you choose yourself in **Edit… ▸ Choose image…** (a
  copy is kept in the data folder's `covers` folder; **Use the store's image** goes back). The band they sit in takes the
  picture's main colour, never so strongly that a text on it gets hard to read (primary and secondary text keep 4.5:1,
  the faintest 3:1, in both themes), and follows a theme switch. A game from itch, the Epic Games Launcher or another
  store has a picture only once you choose one, because those apps keep no image files. **Settings ▸ Games** has *Show
  game artwork* and *Colour the game page from its artwork*, both on. **Privacy Policy 2.11** names the images read and
  the copies kept; FrameLedger still makes no request to any store.

### Changed

- **The list of tested games has its first Vulkan game**: Everhex Demo, measured through FrameLedger's Vulkan layer on
  2026-10-13 when Play started it directly (`docs/LIST_GAME_TESTED.md`, `LIMITATIONS.md`). Four places in the developer
  documents that described something never built, or kept a count that went stale, are corrected in place.

### Fixed

- **A game's page opens and changes session without freezing the window** (owner request 2026-10-14). Measured on the
  dev PC over a ledger shaped like the owner's (`docs/spike-notes.md` §21): a game with 100 sessions took 1.2–1.5 s to
  open — its Sessions list built every row, now only the rows on screen (it scrolls itself and hands the wheel to the
  page at its ends) — 0.37 s now; choosing a two-million-frame session froze the window 0.8–1.0 s — the session was read
  and decoded on the UI thread, then sorted three times for the Distribution tab — 17 ms now: it is read on the thread
  pool and what the charts need from all of it is worked out there once. The page also asks whether the game's `.exe` is
  on disk off the UI thread (a USB drive that sleeps answered on it), and no longer summarises every game to show one.
- **Each visit to the Dashboard or Logs no longer stays in memory.** Every Dashboard ever opened stayed alive and kept
  listening to the capture agent, so at each session's end each one reloaded its lists and raised its own "Session
  saved" notice — twenty visits, twenty notices, the last one shown. The Dashboard listens only while it is on screen,
  and the notice has one home for the App's life, shown once whichever page is open; each Logs page kept its tail of up
  to 2 MB, twice.
- **The Logs page reads its file only when it changed**, not every two seconds, and filters it off the UI thread; **Play**
  reads the stores' lists of installed games off the UI thread (Steam's manifests sit on whatever drive its libraries
  are on). At Debug level the App now logs how long each page took to appear (`ui: page … shown … ms`).
- **The native ring-buffer tests no longer pass or fail by the scheduler's luck** (developers only). The
  hammering-writer test required the reader to keep more than half of the stream, which measured how the operating
  system scheduled two threads: on a hybrid Intel processor it failed 5 of 200 runs with the ring correct every time.
  Both concurrency tests now start the writer only once the reader is running, repeat until the reader really read
  the ring while the writer wrote it, and require that; the small-ring test's old check also passed a reader that
  started after the writer had finished (`src/native/tests/ring_test.cpp`).
