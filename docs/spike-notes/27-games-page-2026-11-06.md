## 27 · Switching to Games, and a language change that lands elsewhere *(2026-11-06, beta.34)*

**Why this was measured.** The owner, 2026-11-06: switching from any page to Games stalls about 0.5–1.5 s before the
page appears; and changing the language in Settings brings back the last content page (a game's detail) instead of
Settings. §21 (beta.23) had measured the library at 275 ms for 48 games and left it, the grid non-virtualizing by the
owner's decision (2026-10-15); the library has 65 games now.

**What the code showed** (read, then measured): every page is transient and rebuilt per visit; `GamesViewModel` read the
settings, the games and the per-game session summary on the UI thread (Microsoft.Data.Sqlite completes its asynchronous
calls synchronously), then asked for every executable's file **and showed no card until all had answered** — 39 of the
owner's 41 Steam games are on the USB drive D:, which sleeps — and cleared and re-added every card on each read; the list
view's `DataGrid` had no height bound and built every row. WPF UI's `NavigationCacheMode` would not have helped: 4.3.0
reads it only when the NavigationView has neither a service provider nor a page provider, and this App sets one. The
language: `ShellHost` remembered only pages opened from code (`PageNavigator`), never a pane click.

**The decision table, written before the runs:** fix what keeps the first card from appearing, what rebuilds a page on
every visit, and what blocks the UI thread ≥ 50 ms; leave the grid non-virtualizing (the owner's decision); record the
rest.

**How.** A scratch xUnit test over the App's own `GamesViewModel` and `GamesPage` (not committed — it times, and a timing
assertion in CI is a flake), Release, on the dev PC of §21: a scratch ledger shaped like the owner's — 65 games, a third
with a session — with the first executable check held **800 ms** (a USB drive waking) and every later one answering at
once. Seven iterations a run, the median; three runs a side, the code before this change (PR-3's tree) and after it.
*First cards*: from the view model's construction to all 65 cards listed. *Build*: a new page laid out at 1200×900 with
its 65 cards. *Revisit*: before, a new page again (every visit built one); after, the kept page laid out again.

| | before (three runs) | after (three runs) |
|---|---|---|
| First cards | 822 – 830 ms | 10 – 15 ms |
| Build (first visit) | 165 – 197 ms | 164 – 223 ms — the same work, run-to-run noise |
| Revisit | 181 – 215 ms | 15 – 16 ms |

**Built** (beta.34): the window keeps the library page it built (`Services.WindowPageCache`, the window's own page
provider, set after `INavigationService.SetNavigationControl`) and the page reads the library again each time it is shown
(`GamesViewModel.Attach`); the library is read on the thread pool; the cards are listed first and the executable checks
follow, each card getting its *Not installed* pill when its check answers; a read keeps every card that would look the
same (`GameCardViewModel.LooksLike`, `GamesViewModel.Sync` — no `Clear`); the list view is bounded (`MaxHeight` 640).
`ShellHost` notes every page the live window shows, so a rebuild opens on Settings after a change made there.

**Left as it was:** the first visit's build (≈ 2.5–3.4 ms a card at 65) — the non-virtualizing grid's cost, unchanged by
decision; a page kept per window holds its 65 cards' visuals for the window's life.
