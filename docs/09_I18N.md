# 09 — Internationalization

Languages: **en** (neutral/default) · **vi** · **ja**. Same `.resx` pattern as the rest of the poli0981 portfolio.

> **Both string families are given the UI culture explicitly (2026-09-21).** `App.ApplyCulture` sets `Strings.Culture`
> AND `FrameLedger.Shared.Strings.Culture`. The second was missing: the safety family fell back to the thread's
> `CurrentUICulture`, and a culture set inside the App's async start flows with that async context, not to the
> dispatcher's later operations — so on an English Windows a Vietnamese UI showed the consent dialog, the refusal
> notices in English (and, for one day, a guard-override card). A resource accessor that depends on which thread asks is the defect;
> `StringsTests.ApplyingTheUiLanguageSetsTheSafetyFamilyToo` holds it with the thread deliberately left English.

## Mechanics

- One `Strings.resx` (+ `Strings.vi.resx`, `Strings.ja.resx`) per assembly that has user-visible text (`App`, `Shared` for error codes). Access through a generated strongly-typed class; **no string literals in XAML/C# for user-visible text** (analyzer TODO: Meziantou MA0011/manual review in PR checklist). **As built (P3 PR-2, 2026-09-13):** the class is `Strings.Designer.cs`, written by `tools/resx-gen.ps1 -Resx <file>` and **committed** — not the SDK's `ResXFileCodeGenerator`, which the SDK-style WPF project does not run — with `Culture`, `ResourceManager`, `Keys`, and one property per key; the audit below fails when it is stale. The first family is `src/FrameLedger.App/Strings.resx` (65 keys); `Shared`'s arrives with PR-4's `Safety_*` text, because an empty family is what the audit refuses.
- XAML binding via `{x:Static res:Strings.Key}` plus a `LocalizeExtension` for the few dynamic cases.
- **Runtime switching:** setting change → set `CultureInfo.CurrentUICulture` + `Thread` defaults → re-create the main window shell (cheap; state preserved via VM). Persist in `settings`.
- `SatelliteResourceLanguages` = `en;vi;ja` in the App csproj to keep publish size down.

## Key conventions

`Area_Element_Qualifier` — e.g. `Games_Header_Sessions`, `Update_Err_RateLimited`, `Chip_RT_Tooltip`. Error dialogs use the code as suffix (`Update_Err404`). Sort keys alphabetically; never reuse a key for different meanings.

## Formatting rules

- Numbers/dates through `CurrentCulture` (`{0:N1}`, `ToString("g")`); **charts and CSV exports always use InvariantCulture** (files must be machine-stable regardless of UI language).
- FPS readout format strings are resources too (`Fps_Fg_Format` = `"{0} → {1} FPS (×{2:0.0} FG)"`) so ja/vi can re-order if needed. **Added 2026-09-03:** `Fps_Presented_Format` = `"{0} FPS"` (the standalone number when frame generation is not measured — `03_METRICS` §Presented FPS), `Fps_Census_NoRuntime` (*"FG not observed"* chip + its tooltip naming the two holes), `Fps_Census_RuntimeLoaded` (*"FG runtime loaded — may include generated frames"*, with `{0}` = module name), and `Fps_Census_NotRun`. *(The unshipped capture host prints ASCII `->` / `x` and `0.##`, not this format; it ships to nobody and is exempt by §Scope below.)*
- No sentence concatenation; use composite format strings with placeholders.
- Pluralization: keep separate keys (`Sessions_Count_One`, `Sessions_Count_Many`) — en/vi/ja all survive this simple scheme.

## Translation workflow

- `en` written first, is authoritative.
- `vi` authored by the maintainer.
- `ja` machine-drafted, each entry marked with `<comment>review</comment>` until reviewed; the About dialog credits reviewers.
- CI check (`tools/resx-audit`): every key present in all three files; ~~missing → build warning list artifact~~ **missing is RED (2026-09-13)**: `tools/resx-audit.ps1` exists since P3 PR-2 as `build.ps1` step 15, self-test first (11 fixture cases, at least four must go red) then the live pass over every `Strings.resx` under `src/`. Per family it requires C#-identifier keys with non-empty neutral values, **exactly** the neutral key set in `vi` and `ja` (a missing key would fall back to English silently; an extra one is dead text), the `Safety_*` rule below, and a current `Strings.Designer.cs`. A tree with no family is red, not green — the gate must not be vacuous.

## Safety-critical strings

Consent, refusal, and safety-unhook text (FR-2.1, `19_SAFETY`) is **reviewed like legal text, not like UI text**:

- No machine-drafted `ja` in this category — a mistranslated ban warning is a real harm. These keys are marked `<comment>safety: human review required</comment>` and ~~the `ja` build fails the resx audit until a human reviewer signs off; until then the `en` string is shown as fallback rather than an unreviewed translation~~ **as built (2026-09-13): the audit is red on a `Safety_*` key in `ja` that carries neither `safety: human review required` nor `safety: reviewed by <name>`, and red on one marked review-required whose value is anything but the `en` string verbatim** — the key-set rule forbids leaving it out, so "shown as `en` until signed" is true by construction (the value IS the English), not by a runtime fallback. Signing = replacing the comment with `safety: reviewed by <name>` beside the reviewed text.
- Never soften the wording per locale. "May result in a permanent ban of your account" must survive translation with the same force in all three languages.
- Key prefix `Safety_*` so they are easy to audit as a group.
- **`Safety_Exception_*` (2026-09-26, D33)** is the user-mode exception's disclosure: the same rules — `ja` ships the
  English verbatim marked for review — and its own version, `AntiCheatExceptionDisclosure.Version`, bumped when any of
  those strings changes meaning, exactly as `SafetyDisclosure.Version` is for `Safety_Consent_*`.
